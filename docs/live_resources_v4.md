# resources-v4 DQfD 实战

新版已接入原 Tkinter 实战窗口。使用已经训练出的 resources-v4 checkpoint，无需重训、重新生成 NPZ 或安装 BC/PPO/CQL Python 包。本入口仅进行推理，不更新模型。

## 启动

在 Windows 的 `soku_ai` 项目根目录执行：

```powershell
python scripts/run_live_ai.py --checkpoint checkpoints/dqfd_resources_v4/last.pt
```

也可以运行 `run_live_ai.cmd`。自动选择优先查找 `checkpoints/dqfd_resources_v4/last.pt` 和 snapshots 的最新文件；界面“浏览”可以选择其他模型。运行中选择另一文件后点击开始，会先停止旧模型，再加载新模型。服务器训练生成的 `.pt` 需先复制到本机，checkpoint 中的 Linux 数据路径不用于实战。

轻量快照不含优化器与 PER，复制和加载通常更省资源，可直接选择 `checkpoints/dqfd_resources_v4/snapshots/step_000001000.pt` 等实际存在的文件。不要把示例文件名当作已经生成的模型。

游戏需要加载支持 `Local\SokuDataBridge.LiveFrames.v1.<PID>` 的 SokuDataBridge.dll，即此前 BC TCN32 已使用的逐帧队列版本。State.v3 仍用于发现游戏与发键前复核。队列缺失会显示明确提示；旧 State.v3 单快照 DLL 不能提供新版所需的完整历史。

如果游戏尚未安装队列版 DLL，需要手动构建并替换游戏实际加载的文件，随后重启游戏。共享 DLL 源码位于同级 `tools/soku-data-monitor`；本次没有修改 DLL 协议，也没有执行编译。已有队列版 DLL 无需因为 DQfD 再次更换。

进入正常人机对战，点击开始。默认控制 1P：

| 游戏动作 | 按键 |
|---|---|
| 上、左、下、右 | W、A、S、D |
| A：体术 | J |
| B：小弹幕 | I |
| C：重弹幕 | L |
| D：DASH | K |

请使游戏设置与窗口按键表一致。F10 全局暂停并松开全部按键；失焦自动暂停。取消“发送按键”可观察模型输出。人机对战主模式 battleMode=2 允许运行，REP 子模式 battleSubMode=2 禁止发键。结束小局后会松键并等待下一局，本次未增加自动菜单重开功能。

## 训练与实战对齐

新版使用 27 个状态数值/标志、5 个类别、每历史行 11 个数值及 4 个类别、每侧最多 3 个对象；字段顺序、版本、归一化形状与有效性会在发键前校验。均值和标准差只读取 checkpoint，不重新拟合，不增加额外 clipping。

防御、擦弹、滞空使用与 REP 转换相同的 frameDataAvailable 和 frameFlags bit 11、10、2；受击状态为 action ID 在 [50,150)。对手弹幕攻击标志仅检查选中的最近三个对象，要求 frameDataAvailable，且存在有效的未旋转攻击框。对象使用 float32 相对坐标/速度，按距控制角色的距离及原序号稳定排序。State.v3 最多发布每侧 128 个对象；若游戏对象超过发布容量，Python 无法恢复未发布对象，最近三个的选择范围会受此限制。

历史从 DLL 实际回读的原始方向、ABCD 建立，不使用计划发送的动作。对于默认 action_shift=1，NPZ 的 action[t-1] 来自采集帧 t，因此使用当前采集帧的输入；action_shift=0 才使用上一采集帧输入。方向持续时间按水平/垂直符号组合连续保持的帧数累计，按钮变化不重置它，也不将其解释为整套动作持续时间。

从连接、暂停恢复或断点重新观察时，持续时间从该连续片段开始计数；无法还原连接前无限长的保持时长。首次连续帧没有可比较的前序，历史无效，与离线片段起点一致。

LiveFrames.v1 缓存最近 128 个完整采集帧。每次推理之间的帧按顺序更新历史，只对最后一帧运行模型。默认积累 32 行有效历史后才推理发键，约需 33 个连续游戏帧；中间帧仅更新历史，避免反复计算对象和神经网络。重复帧不重复计数，回合/进程/侧别变化、KO 和真实缺帧会切断历史，不复制旧状态填满窗口。

输出仍为 144 个 DQfD Q 值，选最大值，按前进/后退、上下及 ABCD 组合解码。相对方向在发键前按最新角色朝向转为物理左右。没有 BC Joint144/Joint432 编号转换，也没有新增动作屏蔽。

## 实战配置与观察

配置文件为 `configs/live_ai.json`：

| 项目 | 默认 | 含义 |
|---|---|---|
| player_side | left | 新版控制 1P；right 为 2P，auto 为按唯一萃香自动选侧 |
| cpu_threads | 1 | 推理进程 PyTorch CPU 线程数，避免小批次的多线程调度开销 |
| device | auto | 自动选设备；也可在窗口选择 cpu/cuda |
| poll_interval_ms | 2 | 队列轮询间隔 |
| max_observation_age_ms | 100 | 观测允许的最大墙钟年龄 |
| max_action_lag_frames | 4 | 发键前最新状态与本次决策状态允许的最大游戏帧差 |
| focus_delay_ms | 300 | 聚焦游戏后发键前的等待时间 |

发键前复核最新状态的进程、回合、侧别、HP、模式和年龄。过期结果会被跳过并松键，下一次继续读取新帧，不永久中断推理。DLL 停止更新也会松键。阈值不是加速按钮，放宽只会容许更旧的决策。

窗口显示实际加载的输入版本、设备/训练 step、所选动作、Q 值 Top-5、发送的键、游戏实际回读的 H/V/A/B/C/D，以及真实历史长度、重置次数和队列缺帧数。推理毫秒包含模型计算、Q 值搬回 CPU 和排名；不含队列读取及状态整理，因此不代表完整端到端控制延迟。

## 防持续站桩模式

`configs/live_ai.json` 默认 `idle_guard_enabled: true`、`idle_guard_max_frames: 60`。界面可勾选和修改帧数，点击“应用”后继续；界面修改仅本次会话生效，持久默认值修改 JSON。60 个游戏帧在正常 60 FPS 下约 1 秒，不按推理次数或暂停时间计时。

只针对动作编号 0（方向和 ABCD 全部松开）：连续实际输出达到上限后，若模型仍选择 0，就改选其余 143 个动作中 Q 最高的一项。成功发键后重新计时，短暂等待仍被允许。暂停、失焦、过期松键、回合切换会清除连续计时；影子推理不干预、不累计。

这是控制端规则，不修改网络、Q 值、训练奖励或 checkpoint。界面分别显示原始最优动作、选用动作和累计干预数，Top-5 仍是原始 Q 排名。它不判断角色实际位移，不禁止蹲防、受击或招式硬直，不能保证替代动作能让角色移动，也不能保证增强实战效果。没有引入固定连招或宏动作。
