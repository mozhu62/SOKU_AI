# 实战推理耗时分析

`LiveAgent.predict` 现在记录主机阶段时间；每30次调用附加一次 CUDA Event 时间线。无逐阶段 synchronize，仅采样推理收尾等待事件完成。诊断存在额外开销，不能冒充零开销测量。

阶段：缓存查找、历史打包/搬运、状态特征、特征检查等待、TCN、当前状态编码、当前帧打包/搬运、对象编码、融合输出头、输出检查/回读等待、CPU动作解码。

主机时间包括 Python 与 CUDA 提交/阻塞；CUDA Event 时间线包括设备执行及可能的主机提交空隙，不是 profiler 的纯 kernel 累计时间。两者重叠，不能求和。NaN/Inf 检查会隐式等待 CUDA，其耗时不能直接归因于检查本身。

总览表及 summary.json 的 inference_breakdown 按稳态/重建分别汇总最近300次已发送决策的 P50/P95 和样本数；被判过期而未发送的推理不在此汇总内。原总推理时间范围是 predict 调用内部，不包含 DLL 读取、ObservationBuilder.build、发键、网页刷新，因此不是端到端控制延迟。各阶段分位数之和也不等于总分位数。

先确认设备、实际精度、Streaming 开关以及新计算帧数。重点比较稳态 TCN 与两处同步等待，再观察搬运及 CPU 解码。重建频繁应先排查缺帧和暂停，不应直接推断网络计算慢。没有 CUDA 事件样本时显示空表/缺项，不填零。

本次仅添加诊断，没有运行测试、编译前端或启动游戏。需要用户重新构建前端、重启实战服务后采集数据；目前没有实测瓶颈结论。
